# BGM推荐器——根据你当前的状态推荐一首歌

## 一、项目概述

请开发一个名为 **「BGM推荐器」** 的现代化 AI 音乐推荐 Web App。

核心理念：

> **用户不用告诉我“我喜欢听什么”，只需要告诉我“我现在是什么状态”，AI 就帮我找到一首适合此刻的歌。**

例如用户输入：

> 加班到凌晨两点，外面一直下着雨，办公室只剩我一个人，有点累，但又不想睡。

AI 应理解用户当前的：

- 情绪
- 场景
- 时间
- 天气
- 活动状态
- 社交状态
- 能量水平

然后推荐 **一首最适合当前状态的歌曲**。

推荐结果必须包含：

1. 歌名
2. 歌手
3. 推荐理由
4. 与当前状态的匹配标签
5. 歌曲封面
6. 播放入口（如果存在合法可用的音乐链接）
7. “换一首”按钮

产品不是传统音乐播放器，而是一个具有 **AI 情绪理解 + 场景推荐 + 情绪陪伴** 属性的轻量级音乐产品。

# 四、AI状态理解

AI不要简单进行关键词匹配，而应该从自然语言中提取结构化状态。

例如：

```json
{
  "emotion": "疲惫",
  "energy": 0.25,
  "scene": "深夜办公室",
  "weather": "雨",
  "time": "深夜",
  "social": "独处",
  "activity": "加班",
  "mood": "低落",
  "desired_effect": "陪伴"
}
```

如果无法判断某个字段：

```text
null
```

不要自行编造。

# 五、歌曲推荐逻辑

推荐模型应该综合：

```text
当前情绪
+
场景
+
时间
+
天气
+
能量水平
+
用户期待
+
歌曲情绪
+
歌曲风格
+
歌曲节奏
```

形成：

```text
Context → Mood Representation → Song Matching → Explanation
```

例如：

用户：

> 今天被老板骂了一顿，回家的地铁上特别烦，不想听太吵的歌。

推荐：

```text
《XXX》
XXX

推荐理由：

今天不太适合用一首歌强行让你开心。
这首歌的节奏比较克制，像是陪你坐完这一段回家的路。
不需要振作起来，先安静一会儿。
```

推荐理由必须自然、具体、有情绪共鸣。

禁止生成模板化：

> “这首歌旋律优美，非常适合你现在的心情。”

# 七、「为什么是这首？」交互

点击后展开 AI 的推荐依据：

```text
为什么是这首？

🌙 深夜
你的输入显示当前处于深夜环境。

🌧️ 雨天
雨天通常适合更加舒缓、空间感较强的音乐。

😮‍💨 疲惫
你的状态能量较低，因此没有推荐节奏过快的歌曲。

🎧 推荐目标
不是让你立刻开心，而是陪你把这一段时间过完。
```

注意：

不要把心理学推断包装成确定事实。

使用：

> “根据你的描述……”

而不是：

> “人在雨天一定会……”

# 八、歌曲数据库

先建立一个结构化歌曲数据库：

```json

  "title": "歌曲名称",
  "artist": "歌手",
  "genre": "indie",
  "mood": [

    "平静"

  "tempo": 75,
  "scene": [
    "深夜",
    "雨天",
    "独处"
  ],
  "language": "zh-CN",
  "cover": "未指定",
  "play_url": "未指定"

```

至少准备 50～100 首歌曲作为 MVP 数据集。

歌曲版权和播放链接必须合法。

如果没有合法播放 API：

```text

```

可以只展示：

```text
歌曲信息
歌曲封面
合法平台跳转链接
```

# 九、推荐算法

MVP使用规则 + 向量相似度即可。

例如：

```text
Score =
0.30 × mood_similarity
+
0.20 × scene_similarity
+
0.15 × energy_similarity
+
0.15 × time_similarity
+
0.10 × weather_similarity
+
0.10 × user_preference
```

如果暂时没有用户历史数据：

```text
user_preference = 0
```

标记为：

```text
未指定
```

后续可以升级为：

```text
Embedding
+
Vector Database
+
LLM Reranking
```

# 十、AI技术方案

推荐：

```text
用户输入
   ↓
LLM
   ↓
结构化状态
   ↓
Embedding
   ↓
歌曲数据库
   ↓
Vector Search
   ↓
Top 10
   ↓
LLM Reranking
   ↓
Top 1
   ↓
生成推荐理由
```

LLM只负责：

- 理解用户状态
- 生成结构化标签
- 对候选歌曲重新排序
- 生成推荐理由

不要让LLM直接“凭空编造歌曲”。

# 十九、隐私

用户输入可能包含个人情绪和生活信息。

因此：

- 默认不保存原始输入
- 不保存敏感个人信息
- 用户主动开启历史记录后才保存
- 提供“清空历史”
- API Key 必须存储在服务器环境变量
- 不允许前端暴露API Key

# 二十一、最终开发要求

请直接按照以上产品需求生成一个**可以运行的完整 MVP**，而不是只生成页面Demo。

要求：

1. 首先建立完整项目结构。
2. 使用 React + TypeScript + Vite。
3. 使用 Tailwind CSS 完成视觉设计。
4. 使用 FastAPI作为后端。
5. 使用SQLite或JSON作为MVP歌曲数据库。
6. AI调用封装为独立Service。
7. 所有API Key使用环境变量。
8. 没有真实API Key时提供Mock模式。
9. Mock模式也必须能够完整演示产品流程。
10. 所有歌曲信息必须来自歌曲数据库，不允许LLM虚构歌曲。
11. 所有不存在的数据使用“未指定”。
12. 支持桌面和移动端。
13. 推荐结果必须具有漂亮的动画过渡。
14. 页面必须有加载状态。
15. AI生成过程中显示具有音乐氛围的Loading动画，例如：
   
   > 正在寻找适合这一刻的声音……

16. API失败时提供友好的错误提示。
17. 推荐失败时允许用户重新生成。
18. 代码必须模块化。
19. README中写清楚安装、运行和环境变量配置方法。
20. 优先保证MVP能够本地运行。

最终产品的核心体验应该非常简单：

```text
我现在是什么状态？
        ↓
告诉AI
        ↓
AI理解我
        ↓
给我一首歌
        ↓
“为什么是这首？”
        ↓
让我觉得：
“卧槽，这首歌真的很适合现在。”
```

请不要在第一版中加入复杂的用户系统、支付系统、社交网络、排行榜和后台管理系统。

**先把“输入状态 → 推荐一首歌 → 解释为什么”这个核心体验做到极致。**
